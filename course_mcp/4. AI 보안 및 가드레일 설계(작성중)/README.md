# AI 보안 및 가드레일 설계

## MCP 기반 에이전트를 안전하게 운영하기

핵심 주제
- 신원 확인
- 최소 권한 원칙
- 서버별 권한 분리
- 신뢰 경계(Trust Boundary)

---
## 강의 목표

이 강의의 목표는 "모델이 똑똑하게 답하게 만들기"가 아니라, **모델이 도구를 써도 사고가 작게 나도록 설계하는 것**입니다.

수강 후 할 수 있어야 하는 일
- MCP 클라이언트, 서버, 사용자, 외부 API 사이의 신원을 구분한다.
- 도구별로 필요한 최소 권한을 정의한다.
- 하나의 거대한 MCP 서버 대신 서버별 권한 경계를 설계한다.
- 프롬프트, 외부 문서, 도구 결과, 인증 토큰 사이의 신뢰 경계를 설명한다.
- 보안 체크리스트로 MCP 서버 설계를 리뷰한다.

---
## 권장 진행 방식

| 차시 | 주제 | 핵심 질문 | 산출물 |
|------|------|-----------|--------|
| 1 | AI/MCP 보안 모델 | 에이전트가 왜 새로운 공격면이 되는가? | 공격면 목록 |
| 2 | 신원 확인 | 지금 요청한 주체는 누구인가? | 신원 매트릭스 |
| 3 | 최소 권한 원칙 | 이 작업에 꼭 필요한 권한은 무엇인가? | 스코프 설계표 |
| 4 | 서버별 권한 분리 | 어떤 기능을 같은 서버에 두면 위험한가? | 서버 분리 아키텍처 |
| 5 | 신뢰 경계 | 어디까지를 믿고, 어디서부터 검증할 것인가? | Trust Boundary 다이어그램 |
| 6 | 종합 설계 | 운영 가능한 가드레일은 무엇인가? | 보안 설계 리뷰 |

---
## 왜 MCP 보안인가?

MCP는 LLM이 파일, DB, API, 검색, 업무 시스템에 접근하는 표준 인터페이스를 제공합니다.

장점
- 모델이 외부 도구와 데이터를 일관된 방식으로 사용할 수 있다.
- 여러 도구를 에이전트 워크플로에 쉽게 연결할 수 있다.
- 로컬 개발, 사내 시스템, 외부 API를 같은 방식으로 노출할 수 있다.

보안 관점의 변화
- 모델 출력이 단순 텍스트가 아니라 **도구 실행 요청**이 될 수 있다.
- 외부 문서와 도구 결과가 모델 행동에 영향을 준다.
- 권한이 넓은 도구 하나가 전체 시스템의 우회 경로가 될 수 있다.

---
## 위협 모델

AI 애플리케이션에서는 전통적인 웹 보안 위협에 더해, 모델 특유의 문제가 생깁니다.

| 위험 | MCP에서의 예 |
|------|--------------|
| 프롬프트 인젝션 | 문서 안의 악성 지시가 모델의 도구 호출을 유도 |
| 민감정보 노출 | 파일 읽기 도구가 토큰, 키, 개인정보를 반환 |
| 과도한 자율성 | 모델이 승인 없이 쓰기, 삭제, 결제, 배포를 실행 |
| 도구/서버 공급망 | 신뢰하지 않은 MCP 서버 패키지를 실행 |
| 토큰 오용 | 다른 서비스용 토큰을 MCP 서버가 그대로 받아 사용 |

---
## 보안 설계의 네 가지 축

1. 신원 확인
   - 사용자, MCP 클라이언트, MCP 서버, 외부 API의 신원을 분리한다.

2. 최소 권한 원칙
   - 처음부터 모든 권한을 주지 않고, 작업 단위로 필요한 권한만 부여한다.

3. 서버별 권한 분리
   - 읽기/쓰기, 내부/외부, 저위험/고위험 도구를 같은 경계에 섞지 않는다.

4. 신뢰 경계
   - 사용자 입력, 검색 결과, 도구 결과, 토큰, 로그를 같은 신뢰 수준으로 취급하지 않는다.

---
## 1. 신원 확인

질문은 하나입니다.

> 이 요청은 누구의 권한으로, 어느 서버에, 어떤 작업을 하려는가?

MCP에서 구분할 신원
- 사용자: 실제 리소스 소유자
- MCP 클라이언트: Cursor, Claude Desktop, 에이전트 앱 등
- MCP 서버: 도구를 노출하고 권한을 검사하는 주체
- 외부 API: GitHub, DB, 사내 API, 클라우드 서비스
- 워크로드: 백엔드 서비스, 배치 작업, 로컬 프로세스

---
## 신원 확인 설계 규칙

| 규칙 | 설명 |
|------|------|
| 세션 ID는 인증이 아니다 | 세션은 상태 추적용이고, 권한 판단은 토큰/정책으로 한다. |
| 토큰의 대상(audience)을 확인한다 | MCP 서버는 자신에게 발급된 토큰만 받아야 한다. |
| 토큰 패스스루를 피한다 | 클라이언트 토큰을 검증 없이 외부 API에 그대로 전달하지 않는다. |
| 서버와 외부 API 토큰을 분리한다 | MCP 서버가 외부 API를 호출할 때는 별도의 권한 모델을 둔다. |
| 감사 로그에 주체를 남긴다 | 사용자, 클라이언트, 서버, 도구명, 요청 ID를 연결한다. |

---
## 실습 1. 신원 매트릭스 만들기

아래 시나리오를 기준으로 신원과 권한을 분리합니다.

시나리오
- 사용자가 에이전트에게 "이번 주 GitHub 이슈를 요약하고 DB에 보고서를 저장해줘"라고 요청한다.
- 에이전트는 GitHub MCP 서버와 SQL MCP 서버를 사용할 수 있다.

작성 항목
- 요청 주체: 누가 요청했는가?
- 실행 주체: 어떤 클라이언트/서버가 실행하는가?
- 리소스 소유자: GitHub 저장소와 DB의 소유자는 누구인가?
- 필요한 권한: 읽기, 쓰기, 수정, 삭제 중 무엇이 필요한가?
- 로그 키: 나중에 추적하려면 어떤 ID를 남겨야 하는가?

## 2. 최소 권한 원칙

최소 권한은 "일단 막기"가 아니라, **작업을 가능하게 하되 피해 범위를 작게 만드는 설계**입니다.

나쁜 예
- `github:*`
- `db:*`
- `files:all`
- `admin`
- `full-access`

좋은 예
- `github:issues:read`
- `github:pull_requests:read`
- `db:reports:insert`
- `files:workspace:read`
- `files:workspace:write`

---
## 권한은 단계적으로 올린다

처음 연결 시
- 도구 목록 조회
- 공개 메타데이터 읽기
- 워크스페이스 내부 읽기

작업 시점에 추가 승인
- 파일 쓰기
- DB INSERT/UPDATE
- 외부 API POST
- 이메일/메신저 발송
- 배포, 삭제, 결제, 권한 변경

운영 원칙
- 고위험 작업은 별도 승인 화면 또는 사람 검토를 둔다.
- 쓰기 권한은 읽기 권한과 분리한다.
- 거절된 권한 요청은 반복 루프를 막는다.

---
## 스코프 설계 예시

| 도구 | 허용 스코프 | 차단할 것 |
|------|-------------|-----------|
| `search_issues` | `github:issues:read` | repo admin, token 읽기 |
| `create_report` | `db:reports:insert` | 임의 테이블 쓰기 |
| `read_note` | `files:workspace:read` | 홈 디렉터리, SSH 키 |
| `write_note` | `files:workspace:write` | 경로 이탈, 실행 파일 덮어쓰기 |
| `send_summary` | `notify:message:send` | 대량 발송, 외부 도메인 무제한 |

---
## 실습 2. 권한 줄이기

다음 권한을 최소 권한으로 다시 쪼개 봅니다.

```text
github:*
db:*
files:all
notify:send
```

힌트
- 읽기와 쓰기를 나눈다.
- 리소스 종류를 나눈다.
- 위험한 작업은 별도 스코프로 분리한다.
- 처음부터 부여할 권한과 실행 중 추가 승인할 권한을 구분한다.

---
## 3. 서버별 권한 분리

MCP 서버는 기능 단위가 아니라 **권한 경계 단위**로 나누는 것이 좋습니다.

나쁜 구조
```text
mega_mcp_server
├─ GitHub 읽기/쓰기
├─ 파일 읽기/쓰기
├─ SQL 읽기/쓰기/삭제
└─ Slack 발송
```

좋은 구조
```text
github_read_server      -> GitHub 읽기 전용
report_db_write_server  -> 보고서 테이블 쓰기 전용
workspace_file_server   -> 지정 폴더 내부 파일 I/O
notification_server     -> 승인된 채널 발송
```

---
## 왜 서버를 나누는가?

서버를 나누면 다음을 분리할 수 있습니다.

| 분리 대상 | 효과 |
|-----------|------|
| 토큰 | 서버별로 다른 토큰과 대상 audience를 사용 |
| 네트워크 | 내부망 접근 서버와 인터넷 접근 서버를 분리 |
| 파일 시스템 | 특정 폴더만 마운트하거나 허용 |
| 로그 | 어떤 서버가 어떤 요청을 처리했는지 명확해짐 |
| 배포 | 고위험 서버만 더 엄격히 검토 가능 |
| 장애 범위 | 한 서버 침해가 전체 권한으로 확산되는 것을 완화 |

---
## 서버 분리 기준

같은 서버에 두기 전에 물어볼 질문
- 두 도구가 같은 데이터를 다루는가?
- 같은 인증 토큰을 써도 되는가?
- 하나가 침해되면 다른 하나의 권한까지 써도 되는가?
- 둘 다 같은 네트워크 접근이 필요한가?
- 둘 다 같은 감사/승인 정책을 가져도 되는가?

하나라도 "아니오"라면 분리 후보입니다.

---
## 실습 3. 서버 분리 설계

요구사항
- GitHub 이슈를 읽는다.
- RAG 검색을 한다.
- 보고서를 DB에 저장한다.
- 저장된 보고서를 Slack에 보낸다.
- 필요하면 워크스페이스 파일에 초안을 쓴다.

설계 항목
- 필요한 MCP 서버 목록
- 각 서버의 토큰과 스코프
- 각 서버의 네트워크 접근 범위
- 각 서버의 파일/DB 접근 범위
- 사람이 승인해야 하는 작업

---
## 4. 신뢰 경계(Trust Boundary)

신뢰 경계는 **검증 없이 넘기면 안 되는 선**입니다.

MCP 애플리케이션의 대표 경계
- 사용자 입력 ↔ 시스템 지시
- 외부 문서/RAG 결과 ↔ 모델 지시
- 모델 판단 ↔ 실제 도구 실행
- MCP 클라이언트 ↔ MCP 서버
- MCP 서버 ↔ 외부 API
- 로컬 파일 시스템 ↔ 서버 작업 디렉터리
- 로그/트레이스 ↔ 민감정보

---
## 신뢰 수준을 다르게 본다

| 입력/출력 | 기본 신뢰 수준 | 처리 방식 |
|-----------|----------------|-----------|
| 시스템 프롬프트 | 높음 | 변경 권한 제한, 노출 최소화 |
| 사용자 프롬프트 | 중간 | 의도 파악, 정책 검사 |
| RAG/웹/문서 | 낮음 | 지시문으로 실행하지 않음 |
| 도구 결과 | 낮음~중간 | 후속 도구 호출 전에 검증 |
| 모델 출력 | 낮음~중간 | 실행 전 정책 검사 |
| 인증 토큰 | 매우 민감 | 저장/로그 금지, 대상 검증 |

---
## 프롬프트와 데이터의 경계

LLM은 프롬프트 안에서 "명령"과 "데이터"를 완벽히 분리하지 못할 수 있습니다.

따라서 설계 원칙은 다음과 같습니다.
- 외부 문서 안의 문장을 시스템 지시처럼 취급하지 않는다.
- RAG 결과가 도구 호출을 직접 지시하게 두지 않는다.
- 모델이 만든 SQL, 경로, URL, 명령은 실행 전에 검증한다.
- 고위험 도구 호출은 사용자 확인 또는 정책 엔진을 통과시킨다.

---
## 토큰과 API의 경계

MCP 서버는 클라이언트가 준 토큰을 그대로 외부 API에 넘기는 프록시가 되면 안 됩니다.

설계 원칙
- MCP 서버용 토큰과 외부 API용 토큰을 분리한다.
- 토큰의 대상(audience)을 검사한다.
- 외부 API 호출은 MCP 서버의 정책과 감사 로그를 거친다.
- 다운스트림 API가 "누가 호출했는지" 추적할 수 있게 한다.

---
## URL과 네트워크의 경계

AI 에이전트가 URL을 만들거나 외부 서버가 URL을 제공할 때는 SSRF를 고려합니다.

검증 항목
- 운영 환경에서 OAuth 관련 URL은 HTTPS를 강제한다.
- 내부 IP, 로컬호스트, 클라우드 메타데이터 주소 접근을 차단한다.
- 리다이렉트 대상도 같은 기준으로 검사한다.
- 허용된 도메인 목록 또는 egress proxy를 둔다.

---
## 가드레일 스택

도구 호출 전
- 사용자/클라이언트/서버 신원 확인
- 요청 의도와 도구 위험도 분류
- 스코프와 리소스 범위 검사
- 고위험 작업 승인 요청

도구 호출 중
- 경로, SQL, URL, 파라미터 검증
- 네트워크/파일 시스템 샌드박스
- 시간 제한, 크기 제한, 호출 횟수 제한

도구 호출 후
- 민감정보 마스킹
- 결과 요약 전 출력 검증
- 감사 로그 저장
- 이상 호출 탐지

신원 확인
- 사용자, 클라이언트, MCP 서버, 외부 API의 신원이 분리되어 있는가?
- 세션 ID만으로 권한을 판단하지 않는가?
- 토큰 audience와 만료를 검증하는가?

최소 권한
- 읽기/쓰기/삭제 권한이 분리되어 있는가?
- `*`, `all`, `full-access` 같은 광범위 스코프를 피했는가?
- 고위험 작업은 실행 시점에 추가 승인을 받는가?

---
## 보안 설계 체크리스트

서버별 권한 분리
- 고위험 도구와 저위험 도구가 같은 서버에 섞여 있지 않은가?
- 서버별 토큰, 네트워크, 파일 시스템 접근 범위가 다른가?
- 서버 침해 시 피해 범위를 설명할 수 있는가?

신뢰 경계
- 외부 문서와 도구 결과를 신뢰하지 않은 입력으로 취급하는가?
- 모델 출력이 실행되기 전에 정책 검사를 거치는가?
- 민감정보가 로그, 프롬프트, 도구 결과에 노출되지 않는가?
